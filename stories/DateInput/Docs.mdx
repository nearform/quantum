# DateInput

DateInput is a field for a single date. The date can be typed, or picked from a
[Calendar](?path=/docs/components-calendar--docs) that opens from the button at
the end of the field. It is [Input](?path=/docs/form-input--docs)'s field, so
the two share their appearance, their sizes and their label and help text
wiring.

<Canvas of={DateInputStories.Default} />

## With a value

The value is a `Date`, or `null` when the field is empty. Pass `value` and
`onValueChange` to control it, or `defaultValue` to leave it to the field.
An invalid `Date` -- `new Date('2024-13-45')`, or an unparsed string from an
API run through `new Date` -- is treated as no date, so the field renders
empty, not failing to render. The same goes for an invalid `min` or `max`,
which is treated as no bound.

## Typing a date

The typed text is read with `format`, a
[date-fns format string](https://date-fns.org/docs/format) that defaults to
`dd/MM/yyyy`. Single digits are accepted, so `1/6/2024` is 1 June 2024, and
the text is rewritten in full when the field loses focus.

A date before the year 1000 has to be typed exactly as `format` writes it,
`01/01/0999` for the default. Anything shorter -- `15/06/20`, or `1/1/0999` --
is taken to be a date still being typed, not the year 20, and is reported as
`'format'` until it is finished.

`onValueChange` is called with the date as soon as the text is a complete,
valid date, and with `null` as soon as it stops being one. Anything else --
half a date, 31 February, a date outside `min` and `max` -- leaves the text as
it was typed and the value `null`.

`null` alone cannot tell an empty field from one holding text that is not a
date, so the second argument says which: `{ text, invalid, reason }`.
`invalid` is `true` when there is text and it is not an acceptable date, and
`reason` says what is wrong with it:

- `'format'` -- the text is not a date: half a date, 31 February, a word.
- `'range'` -- the text is a real date, but outside `min` and `max`.
- `null` -- nothing is wrong: the field holds a date, or is empty.

`onValueChange` is called whenever the date or `reason` changes, so a form
learns that the date went away, that the field is now holding something it
will not send, and which message to show for it. It is not called for edits
that change neither -- another keystroke while the text stays wrong in the
same way, `15/6/2024` retyped over `15/06/2024`, or the rewrite to the full
format on blur. The details are a snapshot of the field at the moment the date
or its validity changed, not a live copy of the text; read the text from the
input's `onChange` if you need every edit.

Each change is judged against the text the field shows now, not against
`value`, so a value the parent sets from outside -- a form reset, a linked
field -- is the starting point for the next edit, and a change is reported
once however long the parent takes to apply it. Picking the day that is
already selected keeps it: the calendar does not toggle a date off, and the
field is cleared by deleting its text.

A controlled parent can decline a change by not applying it, for a rule of its
own. The field keeps what was typed while it has focus, so the user can see
and correct it, and every further change is still reported -- including a
revert to the date the parent holds. While the text shows a date other than
`value`, the input carries `invalidMessage` as its custom validity, so a form
using the browser's own validation will not submit one date while showing
another. When the field loses focus it goes back to `value`, the way a
controlled `<input>` does. Show the reason for the rejection beside the field
yourself; only the parent knows it.

The field also flags that text itself. When it loses focus holding text that
is not a date, it takes the `error` variant's styling and `aria-invalid`, and
drops both as soon as the text becomes a date or is cleared. While the text is
invalid the input also carries a custom validity message, so a form using the
browser's own validation will not submit and will say why. Text that is not a
date gets `invalidMessage`. A real date outside the bounds gets a message that
names them -- "Enter a date on or after 01/06/2024", written in `format` --
or `rangeMessage` if you pass one, since telling someone who typed a real date
to enter a valid one asks them to fix something that is not wrong. Show your
own message beside the field as well, as with any other control; `reason`
says which one.

## Minimum and maximum

`min` and `max` are `Date`s, compared by day: a `min` of `new Date()`
allows today whatever the time. Days outside them are disabled in the calendar,
the calendar cannot be paged past them, and a typed date outside them is not a
value.

If the bounds change and the selected date falls outside them, the field
drops it: `onValueChange` is called with `null` and `reason: 'range'`, the date
stays in the text so the user can see what was rejected, and the field is
flagged as above.

The field switches to `error` on its own when it is left holding text that is

## Disabled

Both the text and the calendar button are disabled. A disabled field posts nothing.

`readOnly` also disables the calendar button, so neither route can change the
date, but unlike `disabled` the field still posts its value, as a read-only
`<input>` does.

## In a form

With a `name`, the field adds a hidden input carrying the date as
`yyyy-MM-dd`, whatever `format` shows. A form posts the same value whichever
way the date is displayed, and it is the value a server expects from
`<input type="date">`. The text input itself has no name.

The hidden input follows the field: it is disabled along with it, so a
disabled field posts nothing, as a disabled `<input type="date">` does, and a
`form` attribute is passed to it so the value reaches a form the field is not
inside.

## Dark mode

<Canvas of={DateInputStories.DarkMode} />

The field's container is `Input`'s and the popup is `Calendar`, so their
backgrounds, borders and the calendar's days follow whatever those components
do in the dark theme, including the `error` variant's switch to
`feedback-error`'s dark half on the border.

The text is DateInput's own, and each part carries its own dark colour: the
typed date takes `foreground-dark`, `feedback-error-dark` or
`feedback-success-dark` by variant, the label `foreground-dark` and the help
text `foreground-muted-dark`. Moving these into `Input` would need their dark
halves to move with them -- without them, error and success text would render
in their light colours on the dark field.

## Accessibility

- The calendar button has no text, so it carries an accessible name,
  `calendarLabel`, which defaults to English. It sits in a 24×24 target, the
  smallest [WCAG 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)
  accepts.
- The format is part of the input's description as well as its placeholder,
  because a placeholder is gone as soon as anything is typed and not every
  screen reader reads one. `formatHint` sets the words, for a language other
  than English or a clearer phrasing such as "For example, 15/06/2024".
- The calendar is optional. Everything it does can be done by typing, which
  is the quicker route for a date of birth and the only one for some readers.
- Opening the calendar moves focus to the selected day, or to today, and the
  arrow keys move between days. Choosing one, or pressing Escape, closes it
  and returns focus to the button.
- `labelText` is associated with the field and `helpText` describes it. An
  `aria-describedby` you pass in is kept alongside both.

## Usage

```tsx
import { useState } from 'react'
import { DateInput } from '@nearform/quantum'

const DateOfBirth = () => {
  const [date, setDate] = useState<Date | null>(null)

  return (
    <DateInput
      labelText="Date of birth"
      name="dateOfBirth"
      max={new Date()}
      value={date}
      onValueChange={setDate}
    />
  )
}
```

# Input

A single-line text field. It renders the label, the field and its help text as
one group, wires them to each other, and puts a clear button at the end of the
field. Giving it `type="search"` also puts a magnifier at the start.

## Sizes

Three heights: `sm` is 37px, `default` is 42px and `lg` is 48px.

The first two come from the design file. `lg` is not in it — it is 48px
because that is the height of a large [Button](?path=/docs/form-button--docs),
so a large field and the button that submits it match.

The height is set on the field rather than added up out of padding and text, so
it holds whatever font size the field inherits, and a disabled field — which
drops its border — is the same height as an enabled one.

<Canvas of={InputStories.Sizes} />

### Matching the other form controls

**The size names do not line up across components, so read the height, not the
name.** An `Input` and a `Select` of the same height are `size="default"` and
`size="lg"`; giving both `size="lg"` puts a 48px input beside a 42px select,
and nothing will warn you.

The `Button` column holds for **every** button variant, not just `primary`.
A button's height is arithmetic rather than a class — padding, line box and
border — and `secondary` is the one variant with a border, so the compound
variants in `Button` take its 2px back out of its padding to keep it level:
`secondary lg` is `py-2.5` where `primary lg` is `py-3`, and `border-box`
counts the difference. Read off the class lists that looks like a 4px
discrepancy; measured, both are 48px. `Button`'s **Sizes** story asserts it in
the browser on every CI run, so a variant that gains a border, or a compound
dropped as redundant, fails rather than quietly moving one button in a row.

So the pairs that line up are:

- **37px** — `Input size="sm"` with `Select size="sm"`
- **42px** — `Input size="default"` with `Select size="lg"`
- **48px** — `Input size="lg"` with `Button size="lg"`, which is the only field
  and button that meet exactly; a 42px field beside a 40px `Button size="md"`
  is 2px out, and `Select` has no 48px tier

Two components defaulting to different ends of the same pair is the trap worth
knowing about: an `Input` with no `size` is 42px and a `Select` with no `size`
is 37px, so a form that leaves both alone is already misaligned. Set `size`
explicitly on every control in a row.

## Icons

The leading icon is drawn at 16×16 and the clear icon at 12×12, and the field
sizes both of them, so an icon passed as `leftSideChild` or `rightSideChild`
comes out at the size the design specifies rather than at the `1em` that
`react-icons` defaults to.

The clear button itself is 24×24 — the smallest target
[WCAG 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)
accepts. It grows into the field's own padding rather than pushing the icon
inwards, so the cross stays where it is drawn.

## Accessibility

- The clear button has no text, so it carries an accessible name of its own.
  `clearLabel` renames it for its context — "Clear search" reads better than
  "Clear input" on a search field.
- `labelText` is associated with the field, and `helpText` describes it rather
  than naming it. An `aria-describedby` you pass in is kept alongside the help
  text rather than replaced by it.
- Both icons are hidden from assistive technology. An icon passed in as
  `leftSideChild` or `rightSideChild` should be too — it repeats what the label
  already says.

## Usage

```tsx
import { useState } from 'react'
import { Input, InputProps } from '@nearform/quantum'

const InputDemo = (props: Omit<InputProps, 'onChange' | 'onClear'>) => {
  const [value, setValue] = useState('')
  const handleOnClear = () => {
    setValue('')
  }
  const handleOnChange = (e: React.FormEvent<HTMLInputElement>) => {
    setValue(e.currentTarget.value)
  }
  return (
    <Input
      value={value}
      onClear={handleOnClear}
      onChange={handleOnChange}
      {...props}
    />
  )
}
export { InputDemo }
```

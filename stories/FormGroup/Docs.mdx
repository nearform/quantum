# Form group

A field is three things that have to agree with each other: a label, a
control, and a message below it. `FormGroup` is what makes them agree.

Most of that agreement is id plumbing — the label's `htmlFor` has to match the
control's `id`, the message's `id` has to appear in the control's
`aria-describedby`, and the control has to be marked `aria-invalid` when the
message is an error. Done by hand it is four ids to keep in step per field,
and the failure is silent: nothing looks wrong, the field simply stops being
announced. `FormGroup` derives all of them from one.

```tsx
import { FormGroup, Label, FieldError } from '@nearform/quantum'

const EmailField = ({ error }) => (
  <FormGroup error={error}>
    <Label>Email</Label>
    <Input type="email" variant={error ? 'error' : 'primary'} onClear={clear} />
    <FieldError />
  </FormGroup>
)
```

### Orientation

`vertical` stacks the three parts. `horizontal` puts the label in a column of
its own and indents the message to line up with the control rather than with
the label, which is what the design file draws.

<Canvas of={FormGroupStories.Orientation} />

### The parts are optional

A group with no label, or no message, is just a group with fewer children.
Nothing shifts to fill the gap, and in horizontal orientation a group with no
label has no empty column to show for it.

Dropping the `Label` drops the visible text, not the control's name. A field
whose label lives somewhere else — a column header, say — takes an
`aria-label` instead, as the middle example does. A placeholder is not a
label.

<Canvas of={FormGroupStories.Parts} />

### Errors

`error` does two things: it gives `FieldError` something to render, and it
marks the control `aria-invalid`. The control's own error styling is a
separate `variant` on the control, so a field can be flagged to assistive
technology without being repainted, and repainted without being flagged —
which is what you want while a field is being typed into.

<Canvas of={FormGroupStories.WithError} />

### One message at a time

Write `FieldDescription` and `FieldError` side by side once and leave them.
The error is the more urgent of the two, so it takes the hint's place rather
than the space below it: set `error` and the hint stands down, and the field
does not change height as it is validated. Clear the error and the hint comes
back.

The hint's id leaves `aria-describedby` with it, since the element it names is
no longer rendered. A field that genuinely needs both messages at once wants a
second element of its own rather than a `FieldDescription`.

### Disabled and required

Set on the group and forwarded to the control, so the state lives in one place

### Any control

The group does not know or care what the control is. Anything that is not a
`Label`, a `FieldDescription` or a `FieldError` is taken to be the control and
gets the wiring — our `Input`, our `Select`, a bare `<input type="date">`, or
something from outside the library.

## What a control has to do

One thing: pass its props on. The group hands the control an `id`, an
`aria-describedby` and an `aria-invalid`, and a control that drops them leaves
the label pointing at an element that does not exist.

That matters most for a wrapper of your own. This looks fine and is not:

```tsx
const Field = () => <Input type="text" variant="primary" onClear={clear} />
// FormGroup passes id and aria-describedby to Field; Field ignores both.
```

```tsx
const Field = props => (
  <Input type="text" variant="primary" onClear={clear} {...props} />
)
// Now they reach the input.
```

The other requirement is that the parts are **direct children** of the group.
A control nested inside a `<div>` of your own is not reached, and neither is a
`FieldError` inside one. If you need that layout, take the ids from
`useFormGroup()` and apply them yourself.

## Dark mode

Toggle the theme in the toolbar to see it.

The hint uses `foreground-muted`, the body-text token that clears AA on every
surface in both modes. The error message is `feedback-red` in light mode
(5.74:1 on the page background) and `red-300` in dark.

`red-300` rather than the more obvious `red-400` because a field can sit on
any of the three surfaces: `red-400` is 4.14:1 on `background-alt-dark` and
would fail WCAG 1.4.3 inside a dark card, where `red-300` is 5.98:1 at its
worst and 12.18:1 at its best.

## Accessibility

- **The error is announced twice over, deliberately.** `FieldError` carries
  `role="alert"`, which announces a message that appears after the page has
  loaded, and its id goes into the control's `aria-describedby`, which
  announces a message that was already there when focus arrives. Neither
  covers both cases alone.
- **`aria-describedby` only ever points at something real.** A group whose
  `error` is set but which renders no `FieldError` marks the control invalid
  and says nothing else — a dangling `aria-describedby` is worse than none,
  because a screen reader announces no description at all rather than falling
  back. The same holds for the hint an error has stood down: it leaves
  `aria-describedby` at the moment it leaves the page.
- **Colour is not the error.** The red border and red text reinforce a message
  that has to say what is wrong in words (WCAG 1.4.1), and `aria-invalid` is
  what carries the state to anyone who cannot see either.
- **Nothing the caller set is overwritten.** A control that arrives with its
  own `id`, `aria-describedby`, `disabled` or `required` keeps it, and the
  group builds the rest of the field around that id rather than replacing it.
  `controlId` is the one override.
- **`aria-invalid="false"` is the exception.** It is the attribute's default
  and reads identically to no attribute at all, so a control carrying it has
  asserted nothing and the group's `error` wins. Without that, a control
  template shipping `aria-invalid={false}` by default would sit in a group
  with an error and render a field that looks invalid, says it is invalid, and
  tells a screen reader it is fine. `true`, `grammar` and `spelling` are real
  assertions and are kept.
- **`aria-describedby` is deduplicated.** `useFormGroup()` hands out the very
  ids the group computes, so a caller who applies them to a control the group
  can also reach would otherwise name the same element twice.
- **`disabled` and `required` are only given to elements that can hold them.**
  Forwarding `disabled` to a `<div>` would render an attribute the browser
  ignores and tell nobody anything.
- **The group is one field.** It renders no landmark and no `role="group"`,
  so a set of related fields still needs a `<fieldset>` and a `<legend>` of
  your own.
- **A group without a `Label` still needs a name.** `FormGroup` wires up
  whatever label it is given; it cannot supply one. Leave the `Label` out and
  the control needs an `aria-label`, or a `Label` elsewhere pointed at it with
  `controlId`.

## Usage

```tsx
import {
  FormGroup,
  Label,
  FieldDescription,
  FieldError,
  Checkbox
} from '@nearform/quantum'

// The message on the group, the placement in the children
<FormGroup orientation="vertical" description="We never share it">
  <Label>Email</Label>
  <Input type="email" variant="primary" onClear={clear} />
  <FieldDescription />
  <FieldError />
</FormGroup>

// Or written inline, which marks the field invalid just the same
<FormGroup orientation="horizontal">
  <Label>Checkbox Label</Label>
  <Checkbox name="form-field-name" />
  <FieldError>Please accept the terms</FieldError>
</FormGroup>
```

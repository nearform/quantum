# IconButton

A button whose content is an icon and nothing else: the close on a dialog, the
actions at the end of a table row, a toolbar.

It is a [Button](?path=/docs/form-button--docs) with the label taken out, and
it imports that component's variants rather than restating them — the two sit
beside each other, so a variant that gained a hover state or a focus ring in
one and not the other would be visible in the gap between them.

One thing it adds, and it is the reason the component exists: `label` is
required. An icon button with no accessible name announces as "button" and
nothing more.

### Naming the button

The label says what the button does, not what the icon is a picture of:
"Delete article", not "bin". A row of icons with nothing else to go on is the
case this component exists for, and the case it is easiest to get wrong.

## Dark mode

Toggle the theme in the toolbar to see it. There is nothing of its own here:
the colours are `Button`'s, so both themes are whatever that component
already does.

## Accessibility

- **`label` is required, and there is no default.** An icon button with no
  accessible name is announced as "button" and nothing else, and unlike a
  missing colour the problem is invisible to everyone it does not affect
  (WCAG 4.1.2). No name can be guessed from an icon, so the type asks for one.
- **Say what the button does, not what the icon shows.** "Delete article"
  beats "bin", and beats "Delete" on a page holding several deletes. The
  label is read on its own, out of the context the icon sits in.
- **A visible label and the accessible name have to agree.** WCAG 2.5.3 asks
  that the accessible name contain the visible text, so that someone speaking
  what they can see reaches the control they are looking at. If the `Tooltip`
  says "Notifications", the `label` starts with "Notifications".
- **The icon must not carry a `title`.** `aria-label` already replaces the
  button's contents when its name is computed, so the icon needs no
  `aria-hidden` — but a `title` on it puts a second, competing name in the
  accessibility tree and a browser tooltip the `Tooltip` did not put there.
- **`aria-labelledby` wins where the name is already on the page**, and an
  `aria-label` of your own overrides `label`. That is the naming order in the
  specification rather than anything this component decides; `label` is simply
  the one that is required. An _empty_ `aria-label` is the exception: it falls
  back to `label` rather than blanking it, because a button that names itself
  and then unnames itself has no reading that is not a mistake.
- **Every size clears the minimum target.** The smallest is 36×36, against the
  24×24 WCAG 2.2 asks for (2.5.8) and the 44×44 it recommends (2.5.5). The
  `Sizes` story measures it.
- **`type` defaults to `"button"`.** A bare `<button>` inside a form submits
  it, and an icon button is most often a close or a remove — the one place
  that default does the most damage. Pass `type="submit"` where you mean it.

a button holding text is a [Button](?path=/docs/form-button--docs), which
takes an icon beside its label through `leftSideChild` and `rightSideChild`.

## Usage

```tsx
import { IconButton, BsTrash, BsX } from '@nearform/quantum'

// Named for what it does
<IconButton icon={<BsTrash />} label="Delete article" variant="danger" />

// A close, which should carry no weight of its own
<IconButton icon={<BsX />} label="Close dialog" variant="tertiary" size="sm" />

// With the name made visible too -- the two have to agree
<Tooltip content="Notifications">
  <IconButton icon={<BsBell />} label="Notifications" variant="secondary" />
</Tooltip>
```

# Radio & radio groups

A set of radios that belong to one question, of which exactly one can be
chosen. For a question where any number of the answers can be true at once,
reach for [CheckboxGroup](?path=/docs/form-checkboxgroup--docs) instead.

```tsx
<RadioGroup legend="Delivery" name="delivery" defaultValue="standard">
  <Radio value="standard" label="Standard" description="3-5 working days" />
  <Radio value="express" label="Express" description="Next working day" />
</RadioGroup>
```

`RadioGroup` is the question and `Radio` is one answer to it; a `Radio` only
works inside a group, which is what makes exactly one of them selected and what
moves the selection with the arrow keys.

`orientation` lays the options out **and** sets which arrow keys move between
them. It used to do only the second, so a horizontal group was a column you
navigated with the left and right arrows; the two were never independent in
practice, because a reader arrows in the direction the options are drawn.

`className` lands on the `<fieldset>`, which is the group's outermost element
and the one to size or space. The gaps between the options are `orientation`'s
job, and `labelPosition` is what right-aligns a column of left-hand labels —
neither needs a class of its own any more.

A `Radio` with no `label` renders as the bare control it has always been, so an
existing `ControlLabel` pairing keeps working. Prefer `label` for anything new:
`ControlLabel` has no way to wire up a per-option hint, and a hint nothing
points at is not announced. `className` lands on the control rather than on the
row — the row is layout, and what a caller wants to restyle is the radio.

## Accessibility

- **A group needs a name.** `legend` is it. Without one the options are a run
  of radios that a reader arriving at the third one cannot place. If the name
  is already on the page — a heading directly above the group — point at it
  with `aria-labelledby` rather than repeating it.
- **Both messages are published to the group, not to the radios.** A screen
  reader announces a fieldset's description when focus first enters it, which
  is where the group's hint and its error are useful. Announcing either on
  every option would be one sentence read four times.
- **`aria-invalid` is the per-radio half of an error**, and it is what draws
  the red border.
- **A hint on one option is wired to that option**, through
  `aria-describedby`. On a radio group that matters more than anywhere else:
  the hint is frequently the whole difference between two choices.

## Dark mode

Every part of the group has a dark half: the legend and labels take the same
`foreground-inverse` the rest of the library's labels do, hints take
`foreground-muted-dark`, and the error takes `red-300` rather than
`feedback-red`, which is 3.66:1 on the dark page background. The invalid border
takes `red-400`: a border owes only 3:1 under 1.4.11, and at 20px across
`red-300` reads as pale grey rather than as red.
